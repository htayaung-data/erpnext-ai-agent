# Qwen ERP Governed Scope Activation And Cross-Family Alignment Roadmap

Status: active enterprise roadmap  
Date: 2026-04-13  
Scope: post-research enterprise roadmap for governed scope activation, cross-family alignment, and shared ambiguity breadth expansion across the ERP AI assistant

## 1. Purpose

This roadmap turns the completed governed scope research program into the next major enterprise implementation chapter.

It exists because the research proved something larger than one feature gap.

The core issue is not only that:

1. supplier direct navigation is missing
2. item/product direct navigation is missing
3. payment-entry ownership is partial
4. ambiguity handling is uneven

The deeper issue is:

1. governed scope is activated unevenly across layers
2. family contracts do not consume approved scope consistently
3. some runtime truths are not represented at the front door
4. some approved families still depend on specialized side paths instead of shared family seams

This roadmap is designed to fix that class of problem systematically.

## 2. Executive Objective

The objective of this chapter is:

1. define governed scope once
2. activate it through a complete full-stack path
3. make it consumable by all compatible family contracts
4. unify ambiguity handling across those activated scopes
5. reduce mixed runtime authority without reinventing the architecture

The target future state is:

1. approved scope is visible consistently in metadata, runtime, and family behavior
2. approved scope is reusable across compatible families
3. unsupported scope fails closed explicitly and consistently
4. ambiguity is handled through typed shared clarification, not one-off phrase repairs

## 3. Non-Negotiable Outcome Conditions

After this roadmap is completed, the program should no longer allow these situations:

1. one scope exists in runtime but not in front-door metadata
2. one scope works in one family but not another compatible family without an explicit policy reason
3. one scope works in detail but not in listing, or in listing but not in detail, without an explicit policy reason
4. one scope exists only in specialized code and not in the shared family contract model
5. ambiguity handling exists, but not uniformly across activated scopes

Important boundary:

This does not mean:

1. every field must be exposed in every family
2. every ERP doctype must be activated at once
3. every family must support every scope

It means:

1. every approved scope must have one explicit policy model
2. every compatible family must consume that approved scope through the same governed rules
3. incompatibility must be a deliberate policy decision, not an accidental gap

## 4. What The Research Program Established

The three research rounds established stable conclusions that this roadmap now adopts as baseline truth.

### 4.1 Strong Existing Assets

The system already has:

1. a strong enterprise contract foundation
2. governed family and capability metadata
3. a real typed fresh-query interpretation model
4. a real entity-reference resolution contract
5. a real entity-detail lane
6. a real clarification and continuation framework
7. strong customer lookup behavior as a reference seam
8. real document/detail support for several operational families

These should be reused, not replaced.

### 4.2 Confirmed Structural Weaknesses

Research proved these structural weaknesses:

1. activation narrowness
2. front-door/runtime misalignment
3. mixed runtime authority
4. specialized-path versus shared-family split
5. clarification breadth debt
6. naming and scope-taxonomy unevenness

### 4.3 Cross-Family Interpretation

The most important interpretation from research is:

1. the system already knows many business concepts
2. the system does not activate and expose them evenly across compatible family contracts

So the next chapter must be:

1. scope-first
2. cross-family
3. contract-backed
4. metadata-driven
5. bounded by approved policy

## 5. Design Principles For This Chapter

This roadmap follows the enterprise development guidelines and extends them with scope-activation rules.

### 5.1 Contract First

Every scope package must begin with:

1. explicit scope definition
2. ownership definition
3. compatibility definition
4. allowed projection definition
5. clarification definition

Runtime changes come only after that.

### 5.2 Full-Stack Activation Or No Activation

No scope should be called active unless all required layers exist together:

1. front-door semantic route
2. capability ownership
3. family/report or approved source mapping
4. follow-up compatibility
5. rendering/projection policy
6. clarification coverage
7. regression verification

Partial activation is one of the main causes of current debt and must stop.

### 5.3 Shared Family Consumption

When a scope is approved, it must be consumable by all compatible families through shared policy.

This means:

1. scope activation is not trapped inside one navigation path
2. scope access is not trapped inside one specialized helper
3. detail, listing, ranking, composite, finance, and follow-up families should consume activated scope through explicit compatibility rules

### 5.4 Policy Over Accident

If one family should not consume a scope, that must be explained by policy:

1. incompatible business meaning
2. unsupported evidence basis
3. unsafe projection
4. unresolved ownership

It must not happen because one seam was forgotten.

### 5.5 Ambiguity Is A Shared Layer

Ambiguity handling must be expanded through:

1. typed ambiguity classes
2. metadata-driven activation
3. shared clarification translation
4. existing pending-clarification continuation

Not through:

1. phrase-specific rescue
2. family-specific prompt hacks
3. renderer-specific lexical branches

## 6. Roadmap Structure

This chapter is divided into seven phases.

The phases are sequential in governance order, but implementation inside a phase may be split into bounded slices.

## 7. Phase A: Governed Scope Access Model

Goal: define the policy model that says what scope exists, who owns it, which families may consume it, and what each family is allowed to do with it.

### A.1 Scope Inventory Consolidation

Deliver:

1. one normalized inventory of currently known governed scopes
2. grouping by scope class:
   - master-data scope
   - document scope
   - financial operation scope
   - analytical scope
   - event/lifecycle scope
3. distinction between:
   - active
   - partial
   - specialized-only
   - deferred

Acceptance:

1. every scope referenced in runtime or research is listed exactly once
2. no scope is described differently in different planning docs without an explicit mapping note

### A.2 Scope Ownership Model

Deliver:

1. one ownership definition per scope
2. ownership classification:
   - primary family owner
   - secondary compatible families
   - prohibited families
3. explicit policy rationale for non-shared scope

Examples of ownership decisions to settle:

1. item/product direct directory ownership
2. payment-entry ownership
3. purchase-invoice listing ownership
4. lifecycle/event-date ownership

Acceptance:

1. every active or planned scope has one primary owner
2. there is no unresolved shared-family competition for active scope

### A.3 Family Compatibility Matrix

Deliver:

1. one compatibility matrix linking scope to family contracts
2. compatibility labels:
   - full consumption
   - projection-only consumption
   - follow-up-only consumption
   - clarification-only consumption
   - not allowed

Families to include:

1. direct navigation
2. entity detail
3. transaction listing
4. ranked entities
5. composite artifact
6. financial summary / aging
7. inventory / product-performance
8. continuation and deictic follow-up layers

Acceptance:

1. every active scope has explicit family compatibility
2. gaps are represented as policy decisions, not invisible omissions

### A.4 Projection And Access Policy

Deliver:

1. per-scope allowed field groups
2. per-family allowed projection sets
3. boundary rules for:
   - names-only
   - standard directory table
   - detail sections
   - ranking-compatible fields
   - financial evidence fields
   - lifecycle/event fields

Acceptance:

1. field exposure is controlled centrally
2. families do not decide ad hoc which fields to expose

### A.5 Clarification Model

Deliver:

1. mapping from scope/family combinations to ambiguity classes
2. classification of:
   - missing entity scope
   - missing document basis
   - missing event target
   - missing metric basis
   - ambiguous reference
   - unsupported current family
   - unsupported current scope

Acceptance:

1. ambiguity is defined as policy
2. ambiguity is not left to local message-branch behavior

## 8. Phase B: Canonical Scope Vocabulary And Metadata Backbone

Goal: make all layers refer to the same scope vocabulary and activation model.

### B.1 Canonical Scope Naming

Deliver:

1. canonical scope IDs
2. canonical grain IDs
3. canonical event/basis IDs
4. alias normalization rules

Known normalization targets include:

1. `item` versus `product`
2. `purchase_invoice` versus invoice-general terms
3. payment-entry language versus collections language
4. lifecycle date basis language across families

Acceptance:

1. the same business scope is not named differently across front door, metadata, runtime, and family contracts without an explicit alias mapping

### B.2 Scope Registry Design

Deliver:

1. one metadata registry or tightly coupled registry pack that defines:
   - scope ID
   - label
   - class
   - primary owner
   - compatible families
   - active state
   - approved source authority
   - projection groups
   - clarification coverage

Acceptance:

1. scope activation is visible and auditable in metadata
2. runtime no longer relies on hidden scattered truth for scope activation

### B.3 Family Activation Metadata Alignment

Deliver:

1. family-level metadata that consumes canonical scope IDs
2. capability mappings aligned to the same IDs
3. report/family mappings aligned to the same IDs
4. entity-reference policy aligned to the same IDs

Acceptance:

1. metadata is full-stack aligned for activated scope

### B.4 Coverage Integrity Rules

Deliver:

1. metadata integrity checks that reject partial activation
2. rules such as:
   - no active scope without owner
   - no active scope without approved source
   - no active scope without family compatibility
   - no active scope without clarification class coverage

Acceptance:

1. incomplete activation fails early in validation

## 9. Phase C: Shared Scope Activation Backbone

Goal: create the reusable runtime seam that activates scope consistently across all layers.

### C.1 Front-Door Scope Activation

Deliver:

1. semantic/front-door resolution that consumes canonical scope metadata
2. typed interpretation output that preserves explicit scope rather than dropping it
3. fail-closed behavior for unsupported but explicitly requested scope

Acceptance:

1. no approved runtime scope remains invisible at the front door
2. no unsupported explicit scope silently collapses into another scope

### C.2 Capability / Family / Source Alignment

Deliver:

1. shared runtime resolution that respects:
   - scope owner
   - compatible families
   - approved source mapping
2. elimination of hidden specialized-only ownership when a shared family path exists

Acceptance:

1. activated scope reaches the correct family path consistently

### C.3 Shared Projection Consumption

Deliver:

1. common scope-aware projection handling for:
   - listing
   - detail
   - ranking
   - composite output
   - financial evidence output

Acceptance:

1. scope fields are not exposed differently only because different renderers guessed differently

### C.4 Follow-Up And Deictic Scope Carryover

Deliver:

1. shared follow-up propagation rules for activated scope
2. same-scope continuation behavior across:
   - listing to detail
   - detail to event/basis question
   - ranking to projection refinement
   - direct reference to deictic follow-up

Acceptance:

1. activated scope remains usable in designed follow-up patterns

1. compatible families consume approved scope through one shared policy model

Deliver:

1. for each specialized-only path:
   - align into shared family path

## 15. What This Roadmap Explicitly Avoids

This roadmap does not authorize:

1. activating all ERP grains at once
2. making every family consume every scope blindly
3. replacing existing contracts with a parallel architecture
4. adding family-local keyword routing to patch activation gaps
5. solving ambiguity one phrase at a time
6. forcing large refactor-first work before bounded scope packages are ready

## 16. Success Criteria

This roadmap is successful only if, after completion:

1. scope activation is full-stack and auditable
2. compatible families consume approved scope consistently
3. unsupported combinations clarify or fail closed explicitly
4. detail/listing/follow-up parity is deliberate and policy-based
5. specialized-only support is either aligned or explicitly governed
6. ambiguity handling is broad, typed, and reusable across activated scope

## 17. Final Direction

The next enterprise chapter is not “add supplier,” “add item,” or “add payment entry” as isolated tasks.

The next chapter is:

1. governed scope activation
2. cross-family alignment
3. shared ambiguity breadth expansion

That is the professional way to make the assistant capable of answering approved ERP scope through all compatible family contracts without reintroducing drift, branch-led behavior, or hidden partial support.
