## 9. Stage B exact source-semantic contract

### 9.1 Eligibility and maximum path count

Stage B is eligible only after the Owner accepts the Stage A receipt and exact allowlist.

The structural cap is:

- at most 16 unique literal regular-blob paths total;
- at most two approved paths per Q category;
- one path may support more than one Q only when the Stage A receipt explicitly maps each Q;
- the executable maximum for the attempt equals the smaller of 16 and the exact number of unique paths accepted by the Owner; and
- no directory, glob, prefix, wildcard, adjacent path, returned URL or implicit dependency is included.

A need for a seventeenth path, a third path for any Q, or any unapproved adjacent path is `blocked_by_adjacent_path` and ends the single attempt in controlled failure. It does not create an automatic expansion gate.

### 9.2 Required source-byte acquisition properties

For each accepted path, a future Stage B method must bind:

- repository, commit and root tree;
- literal path, regular-file mode, blob type and Stage A object ID;
- an object-addressed request, not path-only trust;
- exact final host, URL template, method, media type and response status;
- no redirect, retry, authentication or fallback;
- raw body byte count and SHA-256 before decoding;
- a deterministic proof that the raw body corresponds to the accepted Git blob object ID;
- strict decoding and newline classification;
- exact supporting byte offsets, line range or symbol boundary;
- excerpt SHA-256 over the exact raw-byte interval;
- one paraphrased fact, conditions and limitations;
- named adjacent dependencies without opening them; and
- one disposition: `supported`, `not_supported`, `blocked_by_adjacent_path` or `mismatch_discard`.

### 9.3 Unresolved Stage B transport gap

No committed accepted record freezes:

- an object-addressed Git blob raw-byte endpoint;
- its raw media type or response schema;
- redirect and final-URL behavior for that source surface;
- base64 or other content decoding authority if the response is encoded;
- a direct raw-host contract;
- the byte-to-Git-object verification algorithm and approved executable; or
- an exact Stage B curl command.

The prior metadata contract prohibits blob, Contents API and source-content requests. This package cannot silently turn that prohibition into authority.

Consequently:

- the Stage B network allowlist is empty;
- the Stage B command allowlist is empty;
- no GitHub blob API, raw-content host, Contents API, browser, GitHub UI, clone, fetch, archive or Owner-supplied bundle is selected; and
- a bounded authoritative primary-product contract read plus a later Owner decision is required before Stage B can be executable.

An object-ID-addressed raw Git blob surface is the best architectural candidate because it can preserve the Stage A object binding, but it is not recommended or approved until authoritative endpoint, media, raw-byte and object-verification behavior is frozen.

### 9.4 Byte, decoding and newline policy

If a later Stage B transport is approved:

1. hash and count the exact body bytes before decoding;
2. retain the exact raw bytes outside the repository under the approved custody rule;
3. require strict UTF-8 decoding with no replacement characters;
4. reject a UTF-8 BOM;
5. preserve original bytes and perform no newline normalization;
6. classify newline form as `LF`, `CRLF`, `none_at_eof` or `mixed`;
7. treat `mixed` or another undecidable form as controlled failure;
8. define line numbers from the preserved byte stream, not a rewritten copy;
9. define excerpt hashes from exact byte offsets; and
10. place only hashes, ranges, symbols and paraphrased facts in the canonical receipt.

No full source file is reproduced in this canonical document.

### 9.5 Source-semantic closure

A Q closes only when exact approved source bytes directly support the required fact and every necessary caller, declaration, compile condition or adjacent symbol is inside the accepted allowlist. Product documentation, filenames, SQL identifiers, tests, comments without governing code, other versions, branches, build flags, deployment configuration and synthetic fixtures cannot substitute.

Partial facts may remain visible only under `level_a_e2_controlled_failure`. They cannot be aggregated into complete Q1-Q8 closure.
